# Diagnostic parity spec — dbml-ui vs dbdiagram's open compiler

The reference engine: `holistics/dbml` @ the commit in `parity/upstream-pin.txt`,
package `@dbml/parse` (`packages/dbml-parse/src`), driven headlessly by
`parity/driver/theirs-dump-many.ts`. Our engine: `src/dbml/validate.rs`, driven by
`examples/parity_dump.rs`. Both emit the same normalized JSON for a given `.dbml`
input; the runner (`parity/run.mjs`) diffs them per case.

## The normalized diagnostic

Both engines emit, for every diagnostic:

| field      | ours → normalized                                  | theirs → normalized            |
|------------|----------------------------------------------------|--------------------------------|
| `type`     | `Severity::Error` → `"error"`, `Warning` → `"warning"` | `type` verbatim (`error`/`warning`/`info`) |
| `text`     | `message` verbatim                                 | `text` verbatim                |
| `row`      | byte offset → 1-based line of the source           | `startRow` (Monaco, 1-based)   |
| `column`   | byte offset → **UTF-16 code unit** within the line | `startColumn` (Monaco, UTF-16) |
| `endRow`/`endColumn` | the finding's end offset, same conversion | `endRow`/`endColumn` (exclusive end) |
| `quickFixes` | `short_title` + `new_text` per fix               | `shortTitle` + each edit's `newText` |

Parse errors from both engines are diagnostics too (`type: "error"`, no quick fixes).

## Comparison contract (what the runner gates on)

Per corpus case, both diagnostic lists are compared as **sorted multisets of
the full span tuple `(type, text, row, column, endRow, endColumn)`** —
order-free, multiplicity-significant, spans exact. Their positions are
Monaco-style: 1-based rows, UTF-16 code-unit columns, exclusive end; our dump
converts per line (a multi-byte char like `ñ` is one UTF-16 unit, two bytes —
the fuzz corpus caught it).

Per diagnostic, the **quick-fix multisets of `(shortTitle, newText)`** must match
exactly. A missing quick fix, an extra one, or a different edit text fails the
case.

## Superseded (spec v1 -> v2)

Spec v1 gated only `(type, text, row)` and recorded the column as "not
compared — the two engines anchor at different constructs". The span-parity
mission closed that: the columns are gated at UTF-16 fidelity, and every
family of point-span divergence found since (the fragment anchors, the node
spans, the UTF-16 conversion) is ported. Explanations and categories are
gated with the contract above. See `parity/parity.md` for the standing plan
(the mutation campaign, the quick-fix edit ranges).

## Running

```sh
parity/setup.sh                       # clone + build the pinned upstream
cargo build --release --example parity_dump
node parity/run.mjs                   # full corpus run, exits 1 on divergence
```

## The gates (the full program)

| Command | What it proves |
|---|---|
| `node parity/run.mjs` | Diagnostics: the normalized contract above (plus category, explanation, and the quick-fix multiset with title/isPreferred) matches their compiler on the 75-case corpus (`corpus/`, regenerated by `gen_corpus.py`). |
| `node parity/run_schema.mjs` | The parser's OUTPUT: our `Document` rendered as the normalized `Database` JSON their `interpretFile` produces (see PARITY_SCHEMA_SPEC.md; token positions join as offsets only), deep-diffed with path-qualified reports. |
| `python3 parity/fuzz.py N && CORPUS_DIR=... node parity/run.mjs` (and `run_schema.mjs`) | Differential fuzzing: N grammar-shaped random documents fed to BOTH engines; mismatches name the next rule to port. |
| `cargo test` | The Rust-only properties: robustness fuzzing (`tests/fuzz_smoke.rs` — no panics, in-bounds char-boundary spans, sorted diagnostics, valid quick-fix spans, format idempotency; `FUZZ_SEED` reproduces any case), formatter model preservation (`tests/format_preserves_model.rs` — the formatted source re-renders the same Database JSON), and the SQLite oracle (`tests/sqlite_oracle.rs` — our DDL executed by real sqlite3, the PRAGMA catalog cross-checked against our importer). |

All four run in CI (the `conformance` job in
`.github/workflows/release.yml`).

## The rules of the program

1. A divergence is fixed by porting the source logic that produces it —
   never by patching our output to match theirs.
2. Every port lands with corpus cases that prove it against their
   engine.
3. Parse-status disagreements are first-class findings: they mark
   grammar gaps (their parser accepts, ours rejects — or the reverse).
4. Feature surfaces dbdiagram does not have (the formatter, SQLite) get
   properties and real-world oracles instead of an upstream diff.
